# Exploration: dynamic-asset-count

## Current State

`src/market/assets.ts` exports `ASSET_ALLOWLIST = ['BTCUSDT','ETHUSDT','SOLUSDT'] as const`, the derived union type `AllowedAsset = (typeof ASSET_ALLOWLIST)[number]`, and `isAllowedAsset(asset): asset is AllowedAsset`. This single module fans out to five real consumers:

1. `app/api/cycle/route.ts` — `MAX_ASSETS = ASSET_ALLOWLIST.length` (payload length cap) and `parseCyclePayload` rejects any `symbol` where `!isAllowedAsset(symbol)` with a 400.
2. `src/market/binance.ts` (`BinanceHttpSource.fetchCandles`) — refuses to build a Binance URL for a non-allowlisted asset (T-2 SSRF guard).
3. `src/cycle/pullAssets.ts` (`pullAllAssets`) — iterates `ASSET_ALLOWLIST` itself to server-side-pull every allowlisted asset from Binance.
4. `app/api/decisions/[asset]/narrative/route.ts` — `isAllowedAsset(asset)` gates the `[asset]` path param (400 `BAD_ASSET`), and `getDecisionForAsset(asset: AllowedAsset)` uses the type.
5. `tests/market/assets.test.ts`, `tests/api/cycle.test.ts` — hardcode exact 3-symbol equality and "unknown symbol -> 400" behavior.

Domain types are already asset-count-agnostic: `src/domain/types.ts`'s `Asset = string` (loose alias, NOT `AllowedAsset`), and `Decision`/`DecisionReport`/`Candle` all key off that loose `Asset`. The entire dashboard-ux surface (`OverviewClient.tsx`, `DecisionCard.tsx`, `DirectionFilter.tsx`, `app/(dashboard)/lib/select.ts`) iterates `report.decisions` (whatever length the backend returns) and keys React lists by `decision.asset` string — verified NO hardcoded card count, no asset dropdown/enum, no `AllowedAsset` import anywhere in `app/(dashboard)/**`. `DirectionFilter` only enumerates BUY/SELL/ALL directions, never symbols. `src/narrative/{facts,prompt,client,cache,rateLimit}.ts` are all keyed by generic string asset/client-key; narrative cache's 16-entry LRU is unrelated to asset count. So: the RENDERING path is already fully dynamic today — the constraint is entirely in the validation/ingestion layer.

**CRITICAL FINDING (bigger than the allowlist question) — RESOLVED by user 2026-08-17:** `GET /api/decisions` (the dashboard's poll/read endpoint) and the narrative route's `getDecisionForAsset` fallback BOTH call `pullAllAssets()` on cache miss, which independently re-fetches Binance data for whatever is in `ASSET_ALLOWLIST` — completely bypassing whatever n8n's last `POST /api/cycle` sent. `src/cycle/latest.ts`'s own docstring states this pull-recompute is "NOT the common case ... Expect most calls here to take the recompute path" in the project's stated Vercel serverless deployment, because the module-scope cache is not reliably shared across route instances. This means on real deployment, MOST dashboard reads today already go through this independent pull, not through n8n's payload. This is a deliberate original design decision (faf-platform design.md "Decision: one ingestion route, two data sources" — push from n8n OR pull server-side, explicitly to support "the UI's on-demand read path and offline fixture-driven tests"), not an oversight — but it directly conflicted with the user's stated requirement: "no me interesa que la información de los activos llegue desde ningún otro lugar que no sea el flujo de n8n."

**User decision (orchestrator AskUserQuestion, 2026-08-17): remove the pull-mode fallback entirely.** `GET /api/decisions` (and the narrative route's equivalent fallback) must stop independently pulling Binance data. On cache miss, the read path returns whatever the cache last held from n8n's push (empty/stale, not a fresh independent pull) until n8n's next `POST /api/cycle` lands. This makes "n8n's payload is the only source of asset data" strictly true end-to-end, not just true for the push path. `sdd-propose`/`sdd-design` must define the exact cache-miss behavior (e.g., `GET /api/decisions` returns an explicit "no data yet" empty report shape rather than `null`/error) and update `tests/api/decisions.test.ts` and any fixture-driven tests that relied on pull-mode.

Just relaxing/removing `ASSET_ALLOWLIST` does NOT by itself make the app "n8n-only" — the pull-mode removal above is required in addition to (not instead of) the allowlist decision below.

`app/api/cycle/route.ts`'s `POST` is authenticated via a required `x-faf-shared-secret` header validated against `FAF_CYCLE_SHARED_SECRET` env var (401/403 on missing/mismatched secret) — confirmed via `checkSharedSecret`. This was hardened in the already-archived `n8n-cycle-merge-fix` change (n8n now sends this via a Header Auth credential, not a literal workflow header). So `/api/cycle` is NOT a public-ish endpoint reachable by arbitrary internet traffic — it requires the shared secret. `GET /api/decisions` and `GET /api/decisions/[asset]/narrative` have NO such secret (they are the public dashboard-facing read routes); the narrative route's only per-request gate on the asset dimension is `isAllowedAsset(asset)` on the path param, plus a separate T-3 rate limiter (10 req/60s per client key + 100/hour per instance) that is asset-independent.

## Affected Areas

- `src/cycle/pullAssets.ts` — `pullAllAssets()` iterates `ASSET_ALLOWLIST`; per the resolved decision above, its callers (`GET /api/decisions`, narrative route fallback) must stop calling it — function may become dead code to remove, or retained only if a future explicit offline/test-fixture path still needs it (decide in `sdd-propose`)
- `app/api/decisions/route.ts` — `GET /api/decisions`'s cache-miss branch calls `pullAllAssets()` today; per the resolved decision, this branch must change to NOT pull independently
- `app/api/decisions/[asset]/narrative/route.ts` — `isAllowedAsset()` path-param gate, `AllowedAsset` type on `getDecisionForAsset`, and its own `pullAllAssets()` fallback on cache-miss-and-empty-report (same resolution applies)

- `tests/api/cycle.test.ts` — "rejects a symbol outside the allowlist with 400" test; needs rewriting
- `tests/api/decisions.test.ts` (and any fixture-driven test relying on pull-mode recompute) — needs rewriting for the new cache-miss behavior
- Verified NOT affected: `app/(dashboard)/**` (OverviewClient, DecisionCard, DirectionFilter, select.ts, graphLayout.ts), `src/domain/types.ts` (`Asset = string` already loose), `src/narrative/**` (facts/prompt/client/cache/rateLimit all generic-string-keyed), `n8n/faf-workflow.json` (already N-capable per the just-archived `n8n-dynamic-asset-list` change)

## Approaches

Two decisions were in play; the pull-mode question is now resolved (remove it — see Current State). What remains open is (1) what replaces the fixed enumerated allowlist as the validation boundary for `POST /api/cycle`'s incoming symbols.

1. **Drop the fixed allowlist; rely on shared-secret auth + format/size validation** — Remove `ASSET_ALLOWLIST` as an enumerated list. `POST /api/cycle` keeps requiring the shared secret (already the real trust boundary for this endpoint) and validates each `symbol` against a format regex (e.g. `^[A-Z0-9]{2,20}USDT$`, matching current Binance USDT-pair convention) plus a payload-size cap (`MAX_ASSETS` becomes an explicit standalone constant, e.g. 25, decoupled from any list length) and the existing `MAX_KLINES_PER_ASSET`/`MAX_BODY_BYTES` caps (unchanged — still needed regardless, since the shared secret only proves "this came from n8n," not "this payload is small"). `BinanceHttpSource`'s SSRF guard becomes the same format check (still meaningful even under an authenticated caller, since it prevents malformed/adversarial-shaped symbols from ever reaching a live Binance URL — though with pull-mode removed, `BinanceHttpSource` may no longer be called app-side at all; confirm in design). `AllowedAsset` type is removed or becomes a plain `string` alias; its 2 real call sites (`src/market/assets.ts` itself, `app/api/decisions/[asset]/narrative/route.ts#getDecisionForAsset`) lose compile-time exhaustiveness/narrowing but gain nothing they were actually using it for beyond "this string passed isAllowedAsset."
   - Pros: matches the user's stated intent exactly — n8n's payload becomes the sole determinant of "which assets exist," zero code change needed anywhere in the app when n8n's asset list grows/shrinks; smallest actual diff.
   - Cons: loses `AllowedAsset`'s TypeScript exhaustiveness/narrowing (small blast radius — only 2 real call sites, no covering tests today per codegraph); loses "known-typo protection" (e.g. `ETHUSD` instead of `ETHUSDT` now passes format validation instead of 400ing immediately — though this degrades gracefully into the existing "BinanceHttpSource fetch fails -> emit nothing that cycle" no-error path, consistent with the project's existing failure philosophy, not a new failure mode); the exact regex is a real design choice (USDT-only vs. any Binance symbol shape) that needs an explicit decision.
   - Effort: Medium (touches `assets.ts`, `cycle/route.ts`, `binance.ts`, narrative route, 3 test files; combined with the already-resolved pull-mode removal).

2. **Keep a loose format-based predicate, no longer an enumerated list, but preserve `isAllowedAsset`/`AllowedAsset` as named exports** — Functionally identical validation logic to Approach 1 (format regex + size caps), but keep the existing function/type names and module shape (`isAllowedAsset(asset): boolean`, `AllowedAsset = string`) so all call sites' *code* is untouched (just their meaning changes from "enumerated membership" to "well-formed symbol"). Effectively Approach 1 implemented as a minimal-diff refactor rather than a removal.
   - Pros: smallest possible code churn — no import/call-site changes anywhere, existing docstrings/tests need only their *assertions* updated, not their *call shape*; keeps a single named seam (`isAllowedAsset`) if a future stricter check is ever wanted again.
   - Cons: the name `isAllowedAsset`/`AllowedAsset` becomes misleading (nothing is "allowed" via a list anymore, it's a shape check) — a maintainability/naming smell that should be called out even if accepted; same regex-choice question as Approach 1.
   - Effort: Low-Medium (same touch points as Approach 1, less rename churn).

3. **Keep an enumerated allowlist, but make it environment-configurable instead of a source-code literal** (presented for completeness/tradeoff visibility — conflicts with the user's stated intent, not recommended) — `ASSET_ALLOWLIST` is read from a `FAF_ASSET_ALLOWLIST` env var (comma-separated) at module load, defaulting to today's 3 symbols. `isAllowedAsset` keeps doing real enumerated-membership checking; ops can widen the deployed set without a code deploy.
   - Pros: strongest defense-in-depth (a hard enumerated ceiling even if n8n is somehow compromised or misconfigured); zero change to the SSRF-guard's semantics.
   - Cons: introduces a second source of truth (the env var) that must be kept in sync with n8n's Code-node symbol array — exactly the footgun the user explicitly rejected ("no me interesa que la información... llegue desde ningún otro lugar que no sea el flujo de n8n"); `AllowedAsset` still can't be a compile-time TS union since it's now runtime-derived from an env value, so the type-safety loss happens anyway with none of Approach 1/2's simplicity benefit.
   - Effort: Medium (new env parsing/validation code plus deployment documentation, on top of the same touch points as 1/2).

## Recommendation

**Approach 1** (drop the enumerated allowlist; shared-secret auth + format/size validation becomes the boundary), because it is the only approach that actually satisfies the user's explicit, binding requirement ("no other source than n8n's payload") without introducing a second source of truth. The existing `FAF_CYCLE_SHARED_SECRET` auth already provides the real trust boundary Binance-URL-building and payload-shape currently piggyback on top of — a hard enumerated allowlist is defense-in-depth that is redundant given that trust boundary, not a load-bearing security control on its own (T-2's actual concern, "URLs built only from request input," is fully addressed by format validation, not specifically by enumeration). Approach 2 is an acceptable minimal-diff variant of the same decision if the team prefers to preserve existing call-site shapes; flag as an implementation-detail choice for `sdd-propose`, not a separate architectural fork. Approach 3 should be explicitly declined by the user in `sdd-propose` rather than silently dropped, since it is a real, defensible alternative for anyone prioritizing defense-in-depth over "n8n is the only source" purity — but per the user's own words it does not match what they asked for.

The pull-mode question (see Current State) is now resolved: remove it entirely. This must be scoped into the same change as the allowlist decision — resolving only the allowlist without removing pull-mode would leave the user's requirement false in practice (most dashboard reads would still bypass n8n).

## Risks

- **Cache-miss UX after pull-mode removal**: with `pullAllAssets()` no longer called on cache miss, `GET /api/decisions` needs an explicit defined behavior for "no cached report yet" (e.g., before the very first n8n cycle runs after a deploy, or after a cache eviction). Likely an explicit empty-report shape (`{decisions: [], asOf: null}` or similar) rather than an error — needs to be designed, not left implicit, and the dashboard UI (`OverviewClient.tsx`) needs to handle this empty state gracefully (verify it already has an `EmptyState` component from dashboard-ux — confirm in design phase).
- **Loses "offline fixture-driven tests" rationale**: the original design cited pull-mode as supporting "offline fixture-driven tests." Removing it means those tests need a different data-seeding strategy (e.g., directly seeding `src/cycle/latest.ts`'s cache in test setup, or testing `runCycle` directly without going through the route). Must be scoped into `sdd-tasks`.
- Choosing a symbol-format regex is itself a design decision with a real tradeoff: `^[A-Z0-9]{2,20}USDT$` (locks to USDT-quoted pairs, matching every current v1 asset) vs. a looser `^[A-Z0-9]{2,20}$` (accepts any Binance symbol shape, more future-proof but weaker as a guard). Needs to be picked explicitly, not defaulted silently.
- `MAX_ASSETS`'s replacement value is arbitrary once decoupled from `ASSET_ALLOWLIST.length` — needs an explicit number tied to a stated rationale (e.g. "generous relative to expected N, bounded well below anything that could exhaust memory/CPU," mirroring the existing docstring's own reasoning for the current cap).
- `AllowedAsset`'s type-safety loss is real but narrow: codegraph confirms only 2 actual call sites (`src/market/assets.ts` itself and `narrative/route.ts#getDecisionForAsset`), neither currently covered by tests exercising the type-level guarantee — the loss is more theoretical than currently load-bearing, but should be stated, not silently accepted.
- Existing tests (`tests/market/assets.test.ts`'s exact-3-symbol equality, `tests/api/cycle.test.ts`'s "rejects a symbol outside the allowlist" test, `tests/api/decisions.test.ts`'s pull-mode-dependent assertions) will fail/need rewriting under this change and must be explicitly scoped into `sdd-tasks`.
- `n8n/faf-workflow.json` needs NO change for this work (already N-capable per the archived `n8n-dynamic-asset-list` change) — but the manual live-test this change should include is adding a 4th+ symbol end-to-end through n8n and confirming the app renders N cards without a 400.
- Whether `src/market/binance.ts` (`BinanceHttpSource`) remains used at all after pull-mode removal needs confirmation in design — if its only callers were `pullAllAssets()`, it may become dead code (or retained solely for a still-undecided offline/test path).
